Web Accessibility (A11y)

9 topics · 3 exercises · building an inclusive web for everyone

♿
Why this matters About 1 billion people worldwide — 15% of the global population — live with some form of disability. Accessibility is not a "nice to have" — in many countries it's a legal requirement. More importantly, it makes your website better for everyone.
01

What is Accessibility?

Foundations

Web accessibility means designing and building websites so that people with disabilities can perceive, understand, navigate, and interact with them. The abbreviation A11y stands for "accessibility" — 11 letters between the A and y.

Think about all the different ways people experience the web:

Real User Stories — Different Ways People Use the Web

👁️
Visual Impairment
Min-jun uses a screen reader (NVDA) to browse the web. It reads page content aloud. He navigates by pressing Tab between links and buttons. If your button is a <div>, he can't reach it.
🤝
Motor Disability
Soyeon has limited hand mobility and uses a switch access device — a single button that cycles through focusable elements. She needs large click targets and logical tab order to fill out forms.
🧠
Cognitive Differences
Hyunwoo has dyslexia. He needs clear fonts, generous spacing, and simple language. Flashing animations trigger his anxiety. Good structure — headings and short paragraphs — helps him find information fast.
👂
Hearing Impairment
Yuna is Deaf. She needs captions on all videos and cannot rely on audio cues. Warning sounds must have a visual equivalent. Auto-playing audio is a major barrier.
💡
Accessibility benefits everyone
Curb cuts (ramps at sidewalk edges) were designed for wheelchair users — but they help parents with strollers, delivery workers, and cyclists too. Captions help people in noisy environments. Good color contrast helps people in bright sunlight. A11y is good design.

Key Points

  • Accessibility = designing so people with disabilities can use your site.
  • A11y covers visual, motor, cognitive, and hearing disabilities.
  • 1 billion people worldwide have some form of disability (15% of population).
  • Accessibility improvements benefit all users — not just disabled users.
  • In many countries, inaccessible government and commercial websites are illegal.
02

WCAG Levels

Foundations

The Web Content Accessibility Guidelines (WCAG) are international standards published by the W3C. They define what an accessible website looks like. WCAG 2.1 (current standard) organizes requirements into three levels of conformance:

A
Minimum — Required
The bare minimum. Without these, some users simply cannot use your site at all. Example: images must have alt text. Forms must have labels. Content must not require a color sense to understand.
AA
Standard Target — Expected
This is the target for most websites and is legally required in many jurisdictions. Includes: 4.5:1 color contrast ratio, resizable text up to 200%, keyboard accessible for all features, no seizure triggers.
AAA
Excellent — Enhanced
The gold standard. Not required for whole sites but worth aiming for key features. Examples: 7:1 contrast ratio, sign language for all video content, reading level simplified to lower-secondary.

WCAG Success Criteria — Examples

A (1.1.1) — Non-text content: Every image must have an alt attribute describing it.
A (2.1.1) — Keyboard: All functionality available via keyboard only.
AA (1.4.3) — Contrast: Normal text must achieve 4.5:1 contrast ratio.
AA (2.4.7) — Focus visible: Keyboard focus indicator must be visible.
AAA (1.4.6) — Enhanced contrast: 7:1 ratio for text.
AAA (2.4.9) — Link purpose: Each link's text alone describes its destination.

Key Points

  • WCAG A = minimum — sites must meet this to be usable at all.
  • WCAG AA = standard target — aim for this for all web projects.
  • WCAG AAA = excellent — go here for important, user-facing features.
  • WCAG 2.1 is the current standard; WCAG 2.2 adds more focus-related criteria.
  • The four WCAG principles (POUR): Perceivable, Operable, Understandable, Robust.
03

Semantic HTML

HTML Patterns

Semantic HTML means using elements that describe their meaning — not just their visual appearance. A screen reader doesn't see CSS. It reads the HTML structure and announces what each element is.

Semantic elements give the browser and assistive technology a map of the page: where is the navigation? Where is the main content? What is a footer? Generic <div> elements communicate nothing.

❌ Div Soup — no semantic meaning
<!-- Screen reader: "just a bunch of divs" --> <div id="header"> <div id="logo">My Site</div> <div id="nav"> <div class="link">Home</div> <div class="link">About</div> </div> </div> <div id="main"> <div class="post"> <div class="title">Hello</div> <div class="text">World</div> </div> </div> <div id="footer">© 2026</div>
✅ Semantic HTML — meaningful structure
<!-- Screen reader: "header, navigation, main, article, footer" --> <header> <a href="/">My Site</a> <nav aria-label="Main navigation"> <a href="/">Home</a> <a href="/about">About</a> </nav> </header> <main> <article> <h1>Hello</h1> <p>World</p> </article> </main> <footer>© 2026</footer>

Semantic Element Reference

ElementRoleScreen Reader Announcement
<header>Site or section header"banner landmark" (for page-level header)
<nav>Navigation links"navigation landmark" — users jump directly here
<main>Primary page content"main landmark" — skip-to-main target
<article>Self-contained content"article" — could be read in any context
<aside>Supplementary content"complementary landmark"
<footer>Bottom info / copyright"contentinfo landmark" (for page-level footer)
<section>Thematic grouping"region landmark" (when given an aria-label)
<h1>–<h6>Headings / document outline"Heading level 1: …" — users navigate between headings

Key Points

  • Semantic HTML gives meaning to structure — not just visual appearance.
  • <header>, <nav>, <main>, <footer> create named landmarks screen readers jump to.
  • <article> = self-contained; <section> = thematic grouping (add aria-label).
  • Heading hierarchy (<h1> → <h6>) is how screen reader users skim pages.
  • One <main> per page. One <h1> per page.
04

The <button> vs <div> Problem

HTML Patterns

One of the most common accessibility mistakes is using a <div> or <span> with a click handler instead of a real <button> element. Visually they can look identical — but to assistive technology and keyboard users, they are completely different.

❌ div as button — broken
<!-- This is NOT accessible: --> <div class="btn" onclick="submitForm()"> Submit </div> <!-- Problems: - Not reachable by Tab key - Screen reader: "Submit" (nothing else) - No keyboard activation (Enter/Space) - No disabled state support - No implicit ARIA role -->
✅ real <button> — works for everyone
<!-- This IS accessible: --> <button type="button" onclick="submitForm()"> Submit </button> <!-- Benefits: ✓ Tab focusable by default ✓ Screen reader: "Submit, button" ✓ Activated by Enter and Space ✓ disabled attribute works ✓ Built-in role="button" -->

What <button> gives you for FREE

  • ⌨️
    Keyboard focus: Tab stops here automatically — no tabindex needed.
  • ↵
    Enter & Space activation: Both keys trigger the click — no keydown handler needed.
  • 🔊
    ARIA role built in: Screen readers announce "button" after the label — users know it's interactive.
  • 🚫
    disabled attribute: <button disabled> — automatically not focusable, announced as "dimmed" or "unavailable".
  • 🎨
    Focus style: Browsers provide a default focus ring — you can customize but shouldn't remove it.
⚠️
If you MUST use a non-semantic element…
Add role="button", tabindex="0", and a keydown handler for Enter/Space. But ask yourself first: why not just use <button>? The answer is almost always "we can."

Key Points

  • Use <button> for clickable actions. Use <a href="…"> for navigation links.
  • A <button> is keyboard focusable, screen reader announced, and Enter/Space activatable by default.
  • A <div onclick> has NONE of those behaviors — it's invisible to keyboard and screen reader.
  • Add type="button" to buttons inside forms to prevent accidental form submission.
05

alt Text Deep Dive

HTML Patterns

The alt attribute on <img> elements is the most commonly known accessibility feature — and the most commonly done wrong. The goal is to provide a text equivalent that conveys the same information as the image. The rule is not "describe what you see" — it's "describe the purpose the image serves."

alt Text Decision Tree

Is the image purely decorative? (border, texture, visual flourish with no informational value)
→ Use alt="" (empty alt). Screen readers skip it. Do NOT omit the attribute entirely!
Is the image a link?
→ The alt text should describe the destination of the link, not what the image looks like.
<a href="/home"><img src="logo.png" alt="Gachon University homepage"></a>
Is the image informational? (photo, chart, diagram)
→ Describe what information the image conveys — not just what it looks like.
Bad: alt="chart" · Good: alt="Bar chart showing student enrollment rose 23% from 2024 to 2026"
Is the image text? (screenshot of code, image of a receipt)
→ Always prefer real text. If you must use an image, provide the full text in alt.
HTML — alt text examples
<!-- ❌ Missing alt (WCAG failure — worst case) --> <img src="profile.jpg"> <!-- ❌ Useless alt (screen reader: "image image") --> <img src="profile.jpg" alt="image"> <!-- ❌ Filename as alt (uninformative) --> <img src="profile.jpg" alt="profile.jpg"> <!-- ✅ Informational image --> <img src="profile.jpg" alt="Kim Jisoo, Web Programming student"> <!-- ✅ Decorative image — empty alt --> <img src="decorative-wave.svg" alt=""> <!-- ✅ Complex chart — use figcaption or aria-describedby for longer descriptions --> <figure> <img src="chart.png" alt="Enrollment bar chart — see caption below" aria-describedby="chart-desc"> <figcaption id="chart-desc"> Bar chart: 2024: 1,200 students; 2025: 1,400 students; 2026: 1,476 students. </figcaption> </figure>

Key Points

  • Every <img> must have an alt attribute — with or without a value.
  • Decorative images: alt="" (empty string, not missing) — screen readers skip them.
  • Informational images: describe the purpose/information, not just the visual appearance.
  • Linked images: alt text describes the link destination.
  • For complex images, use <figcaption> or aria-describedby for long descriptions.
06

ARIA Attributes

HTML Patterns

ARIA stands for Accessible Rich Internet Applications. ARIA attributes are added to HTML elements to communicate more meaning to assistive technology — when semantic HTML alone is not enough. The first rule of ARIA: don't use ARIA if native HTML can do it.

AttributePurposeExample
aria-label Provides a text label for an element that has no visible text <button aria-label="Close dialog">✕</button>
aria-describedby Points to another element that provides additional description <input aria-describedby="pwd-hint"> <p id="pwd-hint">Min 8 chars</p>
aria-hidden Hides an element from screen readers (decorative icons, duplicated text) <span aria-hidden="true">🏠</span> Home
aria-live Announces dynamic content changes to screen readers <div aria-live="polite">{status message}</div>
aria-expanded Indicates whether a collapsible section is open or closed <button aria-expanded="false">Menu</button>
role Defines the semantic role of an element (only when no native element exists) <div role="alert">Form saved!</div>
HTML — ARIA in practice
<!-- aria-label: icon-only button --> <button aria-label="Search"> <svg aria-hidden="true">...</svg> </button> <!-- aria-describedby: form field with hint --> <label for="email">Email address</label> <input type="email" id="email" aria-describedby="email-hint" aria-required="true"> <p id="email-hint">We will send a verification link here.</p> <!-- aria-live: live status region --> <div aria-live="polite" aria-atomic="true" id="status"> <!-- JS updates this div — screen reader announces changes --> </div> <!-- aria-expanded: accordion / disclosure pattern --> <button aria-expanded="false" aria-controls="faq-1"> What is accessibility? </button> <div id="faq-1" hidden> Accessibility means designing for everyone... </div>
⚠️
The first rule of ARIA: don't use ARIA
If a native HTML element can express the semantics, use that instead. <button> is better than <div role="button">. <label> is better than aria-label. ARIA is for cases where no HTML element exists (custom dropdowns, tabs, sliders).

Key Points

  • aria-label — provides a label when no visible text exists (icon buttons).
  • aria-describedby — links to additional description text (form hints, tooltips).
  • aria-hidden="true" — hides decorative elements (icons next to text) from screen readers.
  • aria-live="polite" — announces dynamic updates when the user is idle.
  • role — only for widgets without a semantic HTML equivalent.
07

Keyboard Navigation

User Experience

Many users cannot use a mouse — they navigate with the keyboard alone. Your entire website must be fully usable with just Tab, Shift+Tab, Enter, Space, and arrow keys. This is WCAG 2.1.1 — a Level A (minimum) requirement.

Keyboard Navigation Essentials

Tab — Move forward
Moves focus to the next interactive element: links, buttons, inputs, selects. Elements must be natively focusable or have tabindex="0".
Shift+Tab — Move backward
Moves focus to the previous interactive element. Tab order should follow reading order (usually top to bottom, left to right).
Enter / Space — Activate
Enter activates links and buttons. Space activates buttons, checkboxes, and selects. If you use <button>, both keys work automatically.
Arrow Keys — Components
Used inside widgets: radio groups, menus, tabs, sliders. Arrow keys move between options within a component; Tab moves between components.
CSS / HTML — Focus styles & tabindex
/* ✅ :focus-visible — shows focus ring for keyboard, not mouse clicks */ :focus-visible { outline: 3px solid #1a7f5a; outline-offset: 3px; border-radius: 4px; } /* ❌ Never do this — removes focus for keyboard users! */ *:focus { outline: none; } <!-- HTML: tabindex values --> <!-- tabindex="0" — adds element to natural tab order --> <div role="button" tabindex="0" onclick="..." onkeydown="..."> Custom widget </div> <!-- tabindex="-1" — focusable via JS but not by Tab key --> <div id="modal" tabindex="-1">...</div> <!-- Skip navigation link — lets keyboard users jump past nav --> <a href="#main-content" class="skip-link">Skip to main content</a> <nav>...</nav> <main id="main-content">...</main>
💡
Skip Navigation Links
A "skip to main content" link at the top of the page lets keyboard users jump past the navigation menu directly to the content. It can be visually hidden until focused. This is a WCAG AA requirement (2.4.1) for sites with repeated navigation.

Key Points

  • All interactive elements must be keyboard reachable — WCAG Level A.
  • Use :focus-visible for focus styles — visible for keyboard, hidden for mouse clicks.
  • Never set outline: none without an alternative focus indicator.
  • tabindex="0" — adds to tab order; tabindex="-1" — focusable by JS only.
  • Skip links help keyboard and screen reader users jump past repeated navigation.
08

Color Contrast

User Experience

Low color contrast makes text hard to read for people with low vision, color blindness, or anyone in bright sunlight. WCAG defines minimum contrast ratios that text must meet against its background. The contrast ratio is calculated from the relative luminance of foreground and background colors.

Contrast Requirements (WCAG 1.4.3)

Normal text (under 18pt / 14pt bold)
4.5 : 1
WCAG AA minimum
Large text (18pt+ / 14pt+ bold)
3.0 : 1
WCAG AA minimum
Visual Examples — FAIL vs PASS
Pink on white — FAIL (1.4:1) Orange on white — FAIL (2.9:1) Gray #767676 — PASS AA (4.5:1) Gray #595959 — PASS AA (7.0:1) Green + white — PASS AA (5.8:1)

Tools for Checking Contrast

  • 🔍
    WebAIM Contrast Checker — webaim.org/resources/contrastchecker — enter two hex colors, get an instant ratio and WCAG pass/fail.
  • 🎨
    Chrome DevTools — Click any text element in inspector, the color swatch shows contrast ratio and WCAG badge.
  • 🔆
    Lighthouse Accessibility Audit — automatically flags elements with insufficient contrast.
  • 🖱️
    Colour Contrast Analyser (app) — eyedropper tool to check contrast anywhere on screen, including images.

Key Points

  • Normal text: minimum 4.5:1 contrast ratio (WCAG AA).
  • Large text (18pt+ or 14pt+ bold): minimum 3:1 contrast ratio.
  • AAA enhanced: 7:1 for normal text, 4.5:1 for large text.
  • Pure decorative graphics and disabled UI components are exempt.
  • Use Chrome DevTools, WebAIM checker, or Lighthouse to verify ratios.
09

Lighthouse Accessibility Audit

User Experience

Lighthouse is a built-in Chrome DevTools tool that audits your page across five categories: Performance, Accessibility, Best Practices, SEO, and PWA. The Accessibility score checks around 50 automated ARIA and HTML rules. Note: automated tools catch roughly 30–40% of issues — always test with a real screen reader too.

How to Run a Lighthouse Accessibility Audit

  • 1️⃣
    Open your page in Chrome. Right-click anywhere → Inspect (or press F12).
  • 2️⃣
    Click the "Lighthouse" tab at the top of DevTools (may be hidden under ">>" arrow).
  • 3️⃣
    Check only "Accessibility" category (uncheck others for a faster run).
  • 4️⃣
    Click "Analyze page load". Wait 10–20 seconds.
  • 5️⃣
    Read the score (0–100). Expand each failing item to see the exact element and how to fix it.

Reading the Lighthouse Report

Score 90–100 (Green)
Excellent. The automated checks pass. Still manually test with a screen reader and keyboard.
Score 50–89 (Orange)
Needs improvement. Look at the failing items — many are quick fixes (add missing alt text, fix contrast, add labels).
Score 0–49 (Red)
Significant issues. Users with disabilities cannot use the site. Fix critical items first: missing alt, missing form labels, low contrast.
⚠️
Lighthouse is not a complete accessibility test
A score of 100 does NOT mean your site is fully accessible. Lighthouse cannot detect: wrong alt text (it can only check if alt exists), illogical reading order, keyboard traps, confusing language, or poor UX for screen reader users. Always complement with manual testing.

Key Points

  • Lighthouse is in Chrome DevTools → Lighthouse tab → run Accessibility category.
  • Score is 0–100; aim for 90+. Each failing item links to the exact element in the DOM.
  • Automated tools catch ~30–40% of real accessibility issues.
  • Always test with keyboard navigation and a real screen reader (NVDA, VoiceOver, JAWS).
  • Common quick wins: add missing alt text, fix contrast, add form labels, add button text.
