Why Performance Matters

Why & Measure

Web performance is not just about user experience — it directly impacts business outcomes. Studies from Google, Amazon, and Walmart consistently show that slow sites lose users and money.

Performance also affects SEO

Since 2021, Google's Core Web Vitals are ranking signals. Slow pages rank lower in search results. The three Core Web Vitals measure:

  • LCP (Largest Contentful Paint) — how fast is the biggest element visible?
  • CLS (Cumulative Layout Shift) — does the page jump around while loading?
  • INP (Interaction to Next Paint) — how fast does the page respond to clicks?

Key Points

  • 53% of users abandon sites that take 3+ seconds to load.
  • Every 1-second delay = ~7% conversion rate drop.
  • Performance affects SEO — Core Web Vitals are Google ranking factors since 2021.
  • Slower networks (4G, 3G) and slower devices disproportionately affect users in developing markets.

Measuring Performance

Why & Measure

You can't optimize what you don't measure. Lighthouse provides an overall score (0–100) and measures five key metrics. Each metric has "Good", "Needs Improvement", and "Poor" thresholds.

Core Web Vitals & Lighthouse Metrics

MetricFull NameGoodPoorWhat it measures
FCP First Contentful Paint < 1.8s > 3s Time until any content appears (text or image)
LCP Largest Contentful Paint < 2.5s > 4s Time until biggest image/text block is visible
CLS Cumulative Layout Shift < 0.1 > 0.25 How much the layout shifts unexpectedly (0 = no shift)
TBT Total Blocking Time < 200ms > 600ms Time main thread is blocked by heavy JS
SI Speed Index < 3.4s > 5.8s How fast the visible content is displayed overall
💡
Run Lighthouse in Chrome: DevTools (F12) → Lighthouse tab → Check "Performance" → Analyze page load. Run it in Incognito mode to avoid extension interference. Run it multiple times and average the results — scores vary slightly each run.

Key Points

  • Lighthouse scores 0–100. Aim for 90+ (green) for each category.
  • LCP < 2.5s and CLS < 0.1 are the most impactful for user experience.
  • Run Lighthouse in Incognito mode to prevent browser extensions from skewing results.
  • Real-world users (different devices, networks) often see slower times than Lighthouse lab tests.

The Network Tab

Why & Measure

Chrome DevTools Network tab shows every resource your page loads — HTML, CSS, JavaScript, images, fonts, API calls — as a waterfall chart. Each row shows the timing breakdown for one request. This is your primary tool for diagnosing slow pages.

Reading the Waterfall — Request Timing

REQUEST TIMING PHASES
Queueing
Waiting for connection slot
DNS Lookup
Resolving domain to IP address
Connect + SSL
TCP handshake + TLS negotiation
TTFB
Server processing + first byte
Download
Transfer the content bytes
TTFB (Time to First Byte) — the gap between sending a request and receiving the first byte of the response. High TTFB (green bar, >600ms) means the server is slow. Long download (blue bar) means the file is too big.

Network Tab Tips

  • Throttle the network — choose "Slow 4G" or "3G" to simulate mobile users.
  • Sort by Size — find the biggest files dragging down your page.
  • Filter by type — Img, JS, CSS to focus on one resource category.
  • Check "Disable cache" — tests cold load (what new visitors experience).
  • Look for red (4xx/5xx) — failed requests waste user time and may break features.

Key Points

  • The waterfall shows: DNS → Connect → TTFB → Download for every resource.
  • High TTFB = slow server; large download = oversized file.
  • Sort by "Size" to find the biggest resources to optimize first.
  • Use Network throttling to simulate slow mobile connections.
  • Check "Disable cache" to test what a first-time visitor experiences.

Image Optimization

Assets

Images are typically the largest files on any web page — often 60–80% of total page weight. Optimizing images has the highest impact on performance of any single change you can make.

Image Format Comparison

FormatBest ForTypical SizeBrowser Support
JPEG / JPG Photos, complex imagery ~200–500 KB Universal
PNG Transparency, simple graphics, logos ~50–300 KB Universal
WebP Photos & graphics — replaces JPEG & PNG ~30–60% smaller than JPEG 95%+ (all modern)
AVIF Next-gen — best compression ~50% smaller than WebP Good (90%+)
SVG Icons, logos, illustrations (scalable) Very small (text-based) Universal
HTML — Responsive images with srcset
<!-- Basic WebP with JPEG fallback --> <picture> <source srcset="hero.webp" type="image/webp"> <img src="hero.jpg" alt="Campus at sunrise" width="1200" height="600"> </picture> <!-- Responsive srcset: browser picks the right size --> <img src="photo-800.jpg" srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w" sizes="(max-width:600px) 100vw, 800px" alt="Description of image" width="800" height="400"> <!-- Always specify width and height to prevent CLS --> <img src="photo.jpg" alt="..." width="800" height="400">
🔧
Free Image Optimization Tools
Squoosh (squoosh.app) — browser-based, convert to WebP/AVIF and compare quality visually. TinyPNG (tinypng.com) — drag and drop, excellent compression. ImageOptim (Mac app) — batch processing. In VS Code: "Minify Images" or "WebP Converter" extensions.

Key Points

  • Images are usually 60–80% of page weight — optimize these first.
  • WebP is the best choice for most web images — 25–34% smaller than JPEG, works in all modern browsers.
  • Use srcset and sizes to serve the right image size for each screen.
  • Always add width and height attributes on <img> to prevent CLS (layout shift).
  • Use <picture> with a WebP source and JPEG fallback for maximum compatibility.
05

Lazy Loading

Assets

Lazy loading delays loading resources (images, iframes) until they are about to enter the viewport. Images below the fold don't load immediately — the browser loads them only as the user scrolls toward them. This dramatically reduces initial page weight.

HTML — Native lazy loading
<!-- Native lazy loading — one attribute! --> <img src="photo.webp" alt="Gallery photo" loading="lazy" width="600" height="400"> <!-- Also works for iframes --> <iframe src="https://www.youtube.com/embed/xyz" loading="lazy" title="Tutorial video"></iframe> <!-- ❌ NEVER lazy-load the hero/above-fold image! --> <!-- This delays your LCP and hurts your Lighthouse score --> <img src="hero.webp" alt="Hero" loading="lazy"> <!-- WRONG --> <!-- ✅ Hero image: use eager (default) or fetchpriority --> <img src="hero.webp" alt="Hero" fetchpriority="high" width="1200" height="600">

When to Lazy Load and When NOT to

✅ Good to lazy load
  • Image galleries below the fold
  • Long blog post images
  • Product images in a long list
  • Embedded YouTube iframes
  • Map embeds lower on page
❌ Do NOT lazy load
  • Hero / banner image (above fold)
  • Logo in the header
  • Any image visible on load
  • Critical background images
  • First slide in a carousel

Key Points

  • loading="lazy" on <img> and <iframe> — supported by all modern browsers.
  • Lazy loading defers off-screen resources until user scrolls near them.
  • Never lazy load the hero image or any above-the-fold content — it delays LCP.
  • Use fetchpriority="high" on your most important above-fold image to prioritize it.

Minification

Assets

Minification removes all whitespace, comments, and unnecessary characters from CSS and JavaScript files without changing how they work. The result is a smaller file that loads and parses faster.

Before and After Minification

Before (readable, 287 bytes)
/* Navigation styles */ .nav { display: flex; align-items: center; background-color: #1a2340; padding: 12px 24px; } .nav a { color: #ffffff; text-decoration: none; font-weight: 600; }
After minification (108 bytes, 62% smaller)
.nav{display:flex;align-items:center;background-color:#1a2340;padding:12px 24px}.nav a{color:#fff;text-decoration:none;font-weight:600}

Minification Tools & Workflow

Tool / MethodTypeHow to use
cssnanoCSS (Node)npm install cssnano — integrates with PostCSS, webpack, Parcel
TerserJS (Node)npx terser input.js -o output.min.js
npm run buildVite/ReactBuilt-in minification — runs on every production build
CSS MinifierCSS (online)cssnano.co or cssminifier.com — paste and get minified output
VS Code ExtensionBoth"JS & CSS Minifier (Minify)" — right-click to minify
💡
Modern frameworks do this for you
If you use Vite, Create React App, or Next.js — running npm run build automatically minifies all CSS and JS. You write readable code; the build tool creates optimized files for production. Always link the minified files in your deployed site, not the development files.

Key Points

  • Minification removes whitespace, comments, and shortens code — typically 40–70% smaller.
  • Use file.min.css and file.min.js naming convention for minified files.
  • Build tools (Vite, webpack, Parcel) minify automatically in production mode.
  • Combined with gzip/Brotli compression from the server, files can be 80–90% smaller than the original.

JavaScript Loading Strategy

Loading Strategy

By default, when the browser encounters a <script> tag, it stops parsing HTML, downloads the script, executes it, then continues. This "render-blocking" behavior is the most common cause of slow page loads. Two attributes fix this: defer and async.

defer vs async vs none — Execution Order Diagram

No attr: PAUSE
HTML parsing stops → fetch → execute → parsing resumes (SLOW)
async: PAUSE
Fetch while parsing → execute when ready (unpredictable order)
defer:
Fetch in background → execute AFTER full HTML parse (BEST for most scripts)
HTML Parsing Script Fetch Script Execute Blocked/Paused
HTML — Script loading attributes
<!-- ❌ Default — blocks HTML parsing (render-blocking) --> <script src="app.js"></script> <!-- ✅ defer — fetches in background, runs AFTER HTML is fully parsed --> <!-- Preserves order: script1 runs before script2 --> <!-- Best choice for most scripts that need the DOM --> <script src="app.js" defer></script> <!-- async — fetches in background, runs as soon as downloaded --> <!-- Order NOT guaranteed — good for independent scripts (analytics) --> <script src="analytics.js" async></script> <!-- Always put scripts in <head> when using defer/async --> <head> <script src="app.js" defer></script> <script src="analytics.js" async></script> </head>

Key Points

  • Default <script> in <head> blocks HTML parsing — major performance problem.
  • defer — downloads in background, executes after DOM is ready, preserves order. Best for most scripts.
  • async — downloads in background, executes as soon as ready, order not guaranteed. Good for analytics/ads.
  • Both defer and async are only meaningful for external scripts (with src).
  • Use defer as default. Use async only for scripts that don't depend on other scripts or the DOM.
08

Caching

Loading Strategy

Browser caching stores a copy of resources (CSS, JS, images) locally. When a user revisits your site, the browser loads those resources from the local cache instead of downloading them again. This makes repeat visits dramatically faster — often instantaneous.

HTTP Headers — Cache-Control
/* Server response headers — set by your server (Apache/Nginx/Node) */ // Cache for 1 year — for versioned files (CSS/JS with hash in filename) Cache-Control: public, max-age=31536000, immutable // Cache for 1 hour — for frequently updated content Cache-Control: public, max-age=3600 // No cache — for HTML pages that must always be fresh Cache-Control: no-store /* Cache Busting — add version hash to filenames */ /* When you update the file, the hash changes → new URL → browser downloads fresh */ <link rel="stylesheet" href="styles.a3f9c2b1.css"> <script src="app.d8e4f2a9.js" defer></script> /* Build tools (Vite, webpack) add these hashes automatically */

Caching Strategy by Resource Type

ResourceCache DurationWhy
HTML pagesNo cache / shortContent changes; users need fresh HTML to get updated assets
CSS & JS (versioned)1 year (immutable)Filename includes hash; changed file = new URL = fresh download
Images1 month – 1 yearImages rarely change; long cache saves bandwidth
Fonts1 yearWeb fonts never change once deployed
API responsesVariesDepends on data freshness requirements

Key Points

  • Browser caching stores resources locally — repeat visits load instantly from cache.
  • Cache-Control: max-age=31536000 — cache for 1 year (31,536,000 seconds).
  • Cache busting — embed a hash in filenames (e.g., app.d8e4f2.js). Changed file = new URL = no stale cache.
  • Cache HTML with a short duration or no-cache — you want users to always get the latest HTML.
  • Build tools (Vite, webpack) handle cache busting automatically in production builds.

CDN (Content Delivery Network)

Loading Strategy

A CDN is a network of servers distributed around the world. Instead of serving all users from one server (e.g., in Seoul), a CDN serves each user from the nearest server (called an "edge node"). This reduces latency by shortening the physical distance data must travel.

Latency vs Distance — Without and With CDN

❌ Without CDN
User in New York → Seoul server
Distance: ~11,000 km
Round-trip latency: ~200–300ms
Multiple requests × 200ms = very slow
✅ With CDN
User in New York → CDN edge in New York
Distance: ~5 km
Round-trip latency: ~2–5ms
Same content, dramatically faster

Common CDNs You Already Use

CDNUse CaseExample
CloudflareFull site CDN, DDoS protection, free tier availablecloudflare.com — point your domain DNS to Cloudflare
jsDelivrOpen-source libraries (npm packages)cdn.jsdelivr.net/npm/bootstrap@5.3.0/
cdnjsPopular JS libraries (jQuery, etc.)cdnjs.cloudflare.com/ajax/libs/...
Google FontsWeb fonts served globallyfonts.googleapis.com — already a CDN
AWS CloudFrontProfessional site CDN (integrates with S3)cloudfront.net — used by many production sites

Key Points

  • CDN = global network of servers that serve content from the nearest location to each user.
  • Reduces latency by shortening physical distance between server and user.
  • You already use CDNs when you load Bootstrap or jQuery from jsDelivr or cdnjs.
  • Cloudflare offers a free CDN tier — you just point your domain's DNS to them.
  • CDNs also provide automatic gzip/Brotli compression and additional caching.

Quick Wins Checklist

Loading Strategy

Apply these 10 optimizations to any web project for immediate performance gains. Prioritize by impact — the top items give the most improvement with the least effort. Click the checkboxes to track your progress.

10 Performance Quick Wins — Click to check off

  • Convert images to WebP — use Squoosh or TinyPNG to convert all JPEG/PNG images to WebP. Saves 25–34% file size instantly.
    HIGH
  • Add loading="lazy" to below-fold images — one attribute defers images users haven't scrolled to yet.
    HIGH
  • Add defer to all <script> tags — prevents JavaScript from blocking HTML parsing. Huge impact on FCP.
    HIGH
  • Specify width and height on all images — prevents CLS (layout shift). Adds two attributes per image.
    HIGH
  • Minify CSS and JS — run your CSS/JS through a minifier before deploying. 40–70% smaller files.
