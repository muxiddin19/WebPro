What Screen Readers Do
Audio-only web browsing — navigating by keyboard and listening
The challenge: Imagine browsing the web with your monitor turned off. You hear only what the screen reader reads aloud. You navigate with the Tab key, jumping between links and buttons. If an element isn't keyboard-focusable, or if an image has no alt text, it simply doesn't exist for you.

What breaks it
  • ✗ <div> buttons — not focusable, no role announced
  • ✗ Images without alt — skipped silently
  • ✗ Icon-only buttons — announced as blank
  • ✗ Form inputs with no labels — "edit text"
  • ✗ <div> soup — no structure, no landmarks
Common screen readers: NVDA (Windows, free), VoiceOver (Mac/iPhone, built-in), TalkBack (Android), JAWS (Windows, professional)
WCAG — The Accessibility Standard
Web Content Accessibility Guidelines — three levels of conformance
A
Minimum
Required baseline. Without this, some users cannot use the site at all. Example: images must have alt text. All functions keyboard accessible.
AA
Standard Target
Expected by most laws and regulations. Includes 4.5:1 color contrast, focus indicators, text resizable to 200% without losing content.
AAA
Enhanced
Gold standard — not required for all content, but excellent to aim for. Includes 7:1 contrast ratio, sign language videos, simplified reading level.
WCAG is organized around 4 principles — POUR
👀
Perceivable
Info presented in ways everyone can sense
⌨️
Operable
All UI usable by keyboard, not just mouse
🧩
Understandable
Clear language, predictable behavior
🔧
Robust
Works with current and future assistive tech
Semantic HTML vs Div Soup
Same visual output — completely different screen reader experience
❌ DIV SOUP — no meaning
<!-- Screen reader: just a bunch of divs -->

    <div class="link">Home</div>
  </div>
</div>
<div id="content">
  <div class="title">Hello</div>
  <div class="text">World</div>
</div>
✓ SEMANTIC HTML — meaningful
<!-- Screen reader: navigation, main, heading -->
<header>

  </nav>

  <h1>Hello</h1>

Key idea: Screen reader users navigate by landmarks and headings — like a table of contents for the page. Div soup has no table of contents.
The <button> vs <div> Problem
The most common accessibility mistake in modern web development
❌ div as button — broken for keyboard users
<!-- WRONG: keyboard users can't reach it -->
<div class="btn"
     onclick="submit()">
  Submit
</div>

// Problems:
// - NOT focusable by Tab key
// - No "button" role announced
// - No Enter/Space activation
// - No disabled state
✓ <button> — everything for free
<!-- RIGHT: works for everyone -->
<button type="button"
        onclick="submit()">
  Submit
</button>

// Gets for FREE:
// ✓ Tab focusable
// ✓ "Submit, button" announced
// ✓ Enter and Space activate it
// ✓ disabled attribute works
!
Same CSS rule: use <button> for actions, <a href> for navigation links
If it goes somewhere = link. If it does something = button. Never swap them.
✓
If you MUST use a non-semantic element, add: role="button" + tabindex="0" + keydown handler
But ask first: why not use <button>? The answer is almost always "we can."

ARIA — When HTML Isn't Enough
aria-label, aria-describedby, aria-hidden — the three you'll use most
First rule of ARIA: Don't use ARIA if a native HTML element already does the job. <button> beats <div role="button">. ARIA is for widgets that have no semantic HTML equivalent.
<!-- aria-label: provides a text label when no visible text exists -->
<button aria-label="Search">
  <svg aria-hidden="true">...search icon...</svg>
</button>
<!-- Screen reader: "Search, button" (not "graphic, button") -->

<!-- aria-describedby: links to extra description text -->
<label for="pw">Password</label>
<input type="password" id="pw" aria-describedby="pw-hint">
<p id="pw-hint">Minimum 8 characters, one number.</p>
<!-- Screen reader: "Password, edit text: Minimum 8 characters, one number" -->

<!-- aria-hidden: hide decorative elements from screen readers -->
<span aria-hidden="true">🏠</span> Home
<!-- Screen reader only reads "Home", not "house emoji, Home" -->

Critical CSS rules
/* ✓ Use :focus-visible — keyboard only */
:focus-visible {
  outline: 3px solid #1a7f5a;
  outline-offset: 3px;
}

/* ✗ NEVER do this! */
*:focus { outline: none; }

<!-- Skip link: jump past navigation -->
<a href="#main" class="skip-link">
  Skip to main content
</a>
Never remove focus styles
Removing outline: none makes keyboard navigation invisible — WCAG AA failure (2.4.7)
Color Contrast
4.5:1 for normal text · 3:1 for large text · WCAG AA minimum
Who needs good contrast? People with low vision, color blindness, cataracts — and anyone using their phone in sunlight. About 8% of men have some form of color blindness. Good contrast helps everyone.
Visual Examples — Fail and Pass
Pink text on white 1.4:1 ❌ FAIL
Orange on white 2.9:1 ❌ FAIL AA
Gray #767676 4.5:1 ✓ PASS AA
White on green 5.8:1 ✓ PASS AA
White on dark blue 14.5:1 ✓ PASS AAA
AA
WCAG AA — the standard
Normal text: 4.5:1 minimum ratio. Large text (18pt+ or 14pt+ bold): 3:1 minimum.
🔍
Check with tools
Chrome DevTools inspector shows ratio. WebAIM Contrast Checker (webaim.org). Lighthouse accessibility audit flags failures.
aria-live — Dynamic Content
How screen readers hear updates that happen without page reload
The problem: When JavaScript updates content on the page (a cart total, a form error, a search result count), the screen reader user doesn't know. They're focused on a button — the update happened somewhere else. aria-live tells the screen reader: "watch this region, announce any changes."
<!-- aria-live="polite" — announces when user finishes current action -->
<div aria-live="polite" aria-atomic="true" id="status">
  <!-- JS updates this — screen reader announces the new content -->
</div>

<!-- aria-live="assertive" — interrupts immediately (for errors only) -->
<div aria-live="assertive" role="alert" id="error">
  <!-- Errors go here — announced immediately -->
</div>

// JavaScript: update the live region
document.getElementById('status').textContent =
  '5 results found for "accessibility"';
aria-live="polite" — use for
Search result counts · Cart updates · Status messages · Auto-saved confirmations
aria-live="assertive" — use for
Form validation errors · Critical alerts · Session timeout warnings

5 Most Common Mistakes
What breaks accessibility — and how each one affects real users
  • 🖼️
    Missing or bad alt text on images
    Screen reader says "image image" or reads a filename. Fix: add descriptive alt to informational images, alt="" to decorative ones.
  • 🖱️
    <div> and <span> buttons
    Not reachable by keyboard, not announced by screen readers. Fix: use <button> for actions, <a href> for links.
  • 🎨
    Insufficient color contrast
    Light gray text on white, or orange on light background. Fix: check with WebAIM Contrast Checker — minimum 4.5:1 for normal text.
  • 📝
    Form inputs without <label> elements
    Screen reader says "edit text" with no context. Fix: always add <label for="id"> or aria-label to every input.
  • ⌨️
    No skip navigation link
    Keyboard users must Tab through 30+ nav links on every page load. Fix: add a "Skip to main content" link as the first element in <body>.
