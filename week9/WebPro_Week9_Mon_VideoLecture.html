Git & Version Control

Track · Branch · Collaborate · Undo

The Problem
Have you ever done this?
Be honest — we all have
project.html project_v2.html project_FINAL.html project_FINAL_v2.html project_FINAL_USE_THIS.html project_FINAL_USE_THIS_fixed.html project_ACTUALLY_FINAL.html
The problems with this approach
Which one is actually the latest? Who changed what? What if two people edit the same file? How do you undo a change you made three weeks ago?
!
There is a better way
Version control solves all of these problems — and it's the first tool every professional developer learns.
Ch.1 · What is VCS
What is Version Control?
Your code's permanent memory
1
Tracks every change
Who changed what, when, and why — recorded permanently. Even changes from months ago.
2
Who changed what & when
Every change is tagged with the author's name and a timestamp. No more guessing.
3
Roll back to any point in time
Made a mistake? Break something? Instantly revert to any earlier state of your project.
Analogy: Version control is like "Track Changes" in Microsoft Word, but for your entire project — every file, every change, forever.
Ch.1 · Git vs GitHub
Git vs GitHub
They are NOT the same thing
🛠️
Git
● A tool installed on your computer
● Works completely offline
● Records changes in .git/ folder
● Command-line software
● Created 2005 by Linus Torvalds
☁️
GitHub
● A website: github.com
● Hosts your Git history online
● Share projects with the world
● Pull Requests, Issues, Actions
● Owned by Microsoft (2018)
Word vs Google Drive: Git is like Microsoft Word (runs on your machine). GitHub is like Google Drive (cloud storage where you share the files).

Ch.3 · Core Commands
Starting a Repository
git init and git status
# Navigate to your project folder $ cd ~/Desktop/my-project # Initialize a new Git repository $ git init Initialized empty Git repository in .../my-project/.git/ # Check what Git sees (always safe to run) $ git status On branch main No commits yet Untracked files: index.html style.css
Ch.3 · Core Commands
Staging & Committing
git add and git commit
# Stage a specific file $ git add index.html # Or stage ALL changed files at once $ git add . # Commit staged files with a message $ git commit -m "Add navigation menu" [main (root-commit) 4a1b2c3] Add navigation menu 1 file changed, 25 insertions(+)
Packing analogy: git add = put items in a box · git commit = seal the box and label it · The commit message is the label — make it descriptive!

Ch.4 · Branching
Branching — Working in Parallel
A branch is a separate, isolated line of development
main ●────────●──────────────────────────────● ← merge │ ▲ │ git checkout -b feature │ git merge feature feature └───●─────●─────●────────────────────┘ C1 C2 C3
!
main branch = your stable, working code
Never commit broken code directly to main. Keep it deployable at all times.
!
feature branch = your experiment
Create a branch, work freely, break things if needed. Merge back when done.
Analogy: Branching is like making a photocopy of a document to draft edits on — the original is unchanged until you decide to incorporate your changes.
Ch.4 · Branching
Branch Commands
git checkout -b and git merge
# Create AND switch to a new branch $ git checkout -b feature-navbar Switched to a new branch 'feature-navbar' # Make changes, add, commit as usual... $ git add . && git commit -m "Add responsive navbar" # Switch back to main $ git checkout main Switched to branch 'main' # Merge the feature branch into main $ git merge feature-navbar Updating 7b2e9a1..a3f1c2d Fast-forward: index.html | 8 ++++
Ch.5 · GitHub
Connecting to GitHub
Sync your local repository with the cloud
Local Repo
your computer
▶
git push
GitHub
cloud
▶
collaborator pull
Team's Repo
their computer
1
git remote add origin <url>
Link your local repo to GitHub. "origin" is the standard nickname. Do this once per project.
2
git push -u origin main
Upload your commits. After -u, future pushes are just git push.
3
git pull
Download teammates' latest commits. Always pull before starting work.
Ch.5 · Full Workflow
The Complete Daily Workflow
This is what you will do every day as a developer
1. Edit
Make changes to your HTML, CSS, JS files in VS Code
2. git add
Stage the files you want in this commit
3. git commit
Save the snapshot with a descriptive message
4. git push
Upload to GitHub — backs up your work, shares with team
5. git pull
Next day: pull first to get teammates' changes before you start
Repeat this loop every session. Small, frequent commits with good messages are the mark of a professional developer.
Ch.6 · Common Mistakes
Common Mistakes & Fixes
Everyone makes these — knowing them saves hours of frustration
✗
Forgot to git add before committing
Symptom: commit runs but your changed files aren't in it. Fix: always run git status before committing to see what's staged.
✗
Vague commit messages
Message like "update" or "fix" are useless in 3 weeks. Fix: describe what changed AND why. "Fix broken image path in about.html"
✗
Committing directly to main instead of a branch
Breaks team workflow and can push broken code to production. Fix: always git checkout -b feature-name before starting new work.
✗
Forgetting to git pull before starting work
You edit old code while your teammate's changes sit unmerged. Fix: always git pull first thing every session.
