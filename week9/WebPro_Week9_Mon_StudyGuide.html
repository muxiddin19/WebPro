01

Why Version Control?

Imagine working on your web project. You have index.html. You make changes — things break. You want to go back, but you can't remember what you deleted. Sound familiar?

Version control solves this by recording every change you make — who made it, when, and why. You can instantly undo mistakes, browse the full history, and collaborate without overwriting each other's work.

The "filename nightmare" — before version control

// This is what everyone has done... project.html project_v2.html project_FINAL.html project_FINAL_v2.html project_FINAL_USE_THIS.html project_FINAL_USE_THIS_fixed.html project_ACTUALLY_FINAL.html
🤦
The problems: Which is the real final version? Who changed what? What if two people edit at the same time? Version control replaces all of this with one clean, permanent history.
📜
Track History
Every change recorded: what, who, when.
👥
Collaborate
Multiple people edit without overwriting.
⏪
Undo Mistakes
Roll back to any earlier version, instantly.

Key Points

  • Version control tracks every change: what changed, who changed it, when.
  • Replaces "filename_v2_FINAL" chaos with a clean, searchable history.
  • You can undo any mistake — even work from weeks ago.
  • Teams can work on the same files simultaneously without overwriting each other.
02

Git vs GitHub

Students often confuse Git and GitHub. They are related but different things. Git is a tool that runs on your computer. GitHub is a website that hosts your Git history in the cloud.

Word vs Google Drive Analogy

Git is like Microsoft Word — a program installed on your computer to write and track documents locally.
GitHub is like Google Drive — a cloud service where you store and share those documents so others can access them.

Git — the tool

  • Installed on your computer
  • Works completely offline
  • Records changes locally in .git/
  • Command-line tool (CLI)
  • Created by Linus Torvalds (2005)
  • Free, open source

GitHub — the platform

  • Website: github.com
  • Stores your Git history online
  • Share projects with others
  • Pull Requests, Issues, Actions
  • Owned by Microsoft (since 2018)
  • Free for public repos
💡
You can use Git without GitHub — for personal local projects. But GitHub is how teams collaborate and how you back up code to the cloud. GitLab and Bitbucket are popular alternatives.

Key Points

  • Git = the version control software on your machine. Works offline.
  • GitHub = a cloud service that hosts your Git repositories.
  • Git existed before GitHub; you can use Git without it.
  • Other platforms: GitLab, Bitbucket — all host Git repos.

The Git Workflow — 3 Areas

Git tracks your files through three distinct areas. Understanding these areas is the key to understanding Git. Most confusion comes from not knowing which area a file is in.

Moving House Analogy

Working Directory = items scattered around your room — not packed yet
Staging Area = boxes you've packed and labelled — ready to seal
Local Repository = boxes sealed, put in storage with a written inventory
GitHub = a copy of the storage in another city (safe if your house burns down)

Key Points

  • Working Directory: where you edit files. Changes here are not tracked until git add.
  • Staging Area: a holding zone. You choose which changes go into the next commit.
  • Repository: permanent history. Each commit is an immutable snapshot.
  • GitHub is just a remote copy of your local repository, hosted in the cloud.
04

Core Commands

These four commands are what you use every single day. Learn them by doing — they become muscle memory quickly.

Terminal — Starting a repository
# Navigate to your project folder first $ cd ~/Desktop/my-project # Initialize a new Git repository $ git init Initialized empty Git repository in .../my-project/.git/ # Check what Git sees (always safe to run) $ git status On branch main No commits yet Untracked files: (use "git add <file>..." to include in what will be committed) index.html style.css

Reading git status output

Untracked filesNew files Git doesn't know about — run git add
Changes not stagedModified files, not yet added to staging
Changes to be committedFiles staged and ready for next commit
Terminal — Staging and committing
# Stage a specific file $ git add index.html # Stage ALL changed files at once $ git add . # Commit staged files with a descriptive message $ git commit -m "Add navigation menu to index.html" [main (root-commit) 4a1b2c3] Add navigation menu to index.html 1 file changed, 25 insertions(+)
Packing Analogy

git add = put items in a moving box
git commit = seal the box, label it, store it permanently
The commit message is the label — make it descriptive!

⚠️
Good commit messages matter! Write what changed AND why.
Bad: "update"  ·  Good: "Fix broken link in navbar — was pointing to /about instead of about.html"

Key Points

  • git init — creates a new repo in the current folder (makes a hidden .git/ directory).
  • git status — shows what's changed. Run this constantly — it's always safe.
  • git add <file> — stages a file. git add . stages all changes.
  • git commit -m "message" — saves a permanent snapshot of staged files.
05

Viewing History — log & diff

git log shows the full commit history of your project. git diff shows exactly what changed in a file, line by line — essential for reviewing your work before committing.

Terminal — git log
$ git log commit a3f1c2d8e9b4056f1c7a3e81f5d29a04e62b8f40 Author: Muhiddin <m.student@gachon.ac.kr> Date: Mon Oct 27 09:35:12 2026 Add contact form to index.html commit 7b2e9a1f4c8d03e5b6f2a19c4d7e80f3b1c5d9e2 Author: Muhiddin <m.student@gachon.ac.kr> Date: Sun Oct 26 22:14:07 2026 Initial commit — basic HTML structure # Compact one-line view (best for quick scanning) $ git log --oneline a3f1c2d Add contact form to index.html 7b2e9a1 Initial commit — basic HTML structure
Terminal — git diff
# Show unstaged changes (what you've edited but NOT yet git add-ed) $ git diff diff --git a/index.html b/index.html --- a/index.html +++ b/index.html @@ -10,6 +10,8 @@ <nav> <a href="/">Home</a> + <a href="/about">About</a> + <a href="/contact">Contact</a> </nav> # Lines starting with + are ADDED (green in most terminals) # Lines starting with - are REMOVED (red in most terminals) # Show what is staged and about to be committed $ git diff --staged

Key Points

  • git log — shows all commits (newest first): hash, author, date, message.
  • git log --oneline — compact view; great for scanning history.
  • git diff — shows changes in working directory (not yet staged).
  • git diff --staged — shows changes staged and about to be committed.
  • + lines = added; - lines = removed.
06

Branching

A branch is a separate line of development. The main branch (called main) holds your stable, working code. You create a new branch to work on a feature without breaking main. When done, you merge it back.

Branching is what makes professional team development possible — everyone works on their own branch and merges when done.

Branch & Merge Diagram

main ●────────●────────────────────────────● ← merge │ ▲ │ git checkout -b feature │ git merge feature feature └──●─────●─────●──────────────────────┘ C1 C2 C3
Terminal — Branch commands
# List all branches (* marks the current one) $ git branch * main # Create AND switch to a new branch in one step $ git checkout -b feature-navbar Switched to a new branch 'feature-navbar' # Make changes, then add and commit as usual $ git add . && git commit -m "Add responsive navbar" # Switch back to main $ git checkout main Switched to branch 'main' # Merge feature-navbar into main $ git merge feature-navbar Updating 7b2e9a1..a3f1c2d Fast-forward index.html | 8 ++++++++
✅
Best practice: Make new features on a new branch. Keep main clean and always working. Never commit broken code directly to main.

Key Points

  • git branch — lists all branches; asterisk shows current branch.
  • git checkout -b <name> — creates AND switches to a new branch.
  • git checkout <name> — switches to an existing branch.
  • git merge <name> — merges the named branch into your current branch.
  • Keep main stable; develop on feature branches.
07

Working with GitHub

Once your project is on GitHub, you can share it, back it up, and collaborate. The key commands for syncing between your local repository and GitHub are push, pull, and clone.

Terminal — Connecting to GitHub
# After creating an empty repo on github.com, link your local repo $ git remote add origin https://github.com/yourusername/my-project.git # First push: -u sets upstream so future pushes are just "git push" $ git push -u origin main Enumerating objects: 3, done. Branch 'main' set up to track remote branch 'main' from 'origin'. # Future pushes: just this $ git push # Get the latest changes from GitHub (do this before starting work!) $ git pull # Download a repo from GitHub to your computer for the first time $ git clone https://github.com/yourusername/my-project.git

Command reference

git remote add origin <url>Links local repo to GitHub. "origin" is the standard nickname. Do once per project.
git pushUploads your local commits to GitHub.
git pullDownloads GitHub commits and merges into your local branch.
git clone <url>Downloads an entire repo from GitHub to your computer (first time only).

Key Points

  • git remote add origin <url> — connects your local repo to GitHub. Run once.
  • git push -u origin main — first push; -u sets upstream so future pushes are just git push.
  • git pull — always pull before starting work to get your teammates' latest changes.
  • git clone <url> — used on a new machine to download the project for the first time.
08

The GitHub Collaboration Flow

The standard workflow for contributing to someone else's project uses forks and pull requests. This is how millions of open-source contributors work every day — and how your future team projects will work.

The 6-Step Collaboration Cycle

  1. 1
    Fork — On GitHub, click "Fork" to copy someone's repo to your own account.

    You now have your own copy to modify freely.

  2. 2
    Clone — Download your fork to your computer.

    git clone https://github.com/YOUR-USERNAME/the-project.git

  3. 3
    Branch — Create a branch for your specific change.

    git checkout -b fix-broken-link

  4. 4
    Edit → Add → Commit — Make your changes and commit them.

    git add . && git commit -m "Fix broken link in navbar"

  5. 5
    Push — Upload your branch to your fork on GitHub.

    git push -u origin fix-broken-link

  6. 6
    Pull Request — On GitHub, click "New Pull Request" to propose your changes to the original repo owner.

    They review, comment, and decide to merge or request changes.

💡
Pull Request = a proposal, not an action. You are asking the repo owner to "pull" your changes into their project. The full cycle: Fork → Clone → Branch → Edit → Commit → Push → Pull Request.

Key Points

  • Fork = copy a repo to your GitHub account (done on the website).
  • Clone = download any GitHub repo to your local machine.
  • Pull Request (PR) = propose your changes to the original repo owner.
  • The cycle: Fork → Clone → Branch → Edit → Commit → Push → Pull Request.

Interactive Exercises

Follow these terminal commands step by step on your own computer. Each exercise builds on the one before it.

E1

Create Your First Repository

Goal: Initialize a Git repository, create a file, and make your first commit.
# 1. Create a new project folder and enter it $ mkdir my-first-git && cd my-first-git # 2. Initialize Git $ git init Initialized empty Git repository in .../my-first-git/.git/ # 3. Create a simple HTML file $ echo "<h1>Hello Git</h1>" > index.html # 4. Check status — index.html should be "Untracked" $ git status Untracked files: index.html # 5. Stage the file $ git add index.html # 6. Commit it with a descriptive message $ git commit -m "Initial commit: add index.html" [main (root-commit) abc1234] Initial commit: add index.html 1 file changed, 1 insertion(+) # 7. View the log — you should see your commit $ git log --oneline abc1234 Initial commit: add index.html
E2

Create a Branch and Merge It

Goal: Create a feature branch, add a change, then merge it back to main. Observe how files appear and disappear as you switch branches.
# (Continue from E1, or use any existing git repo) # 1. Create and switch to a new branch $ git checkout -b feature-style Switched to a new branch 'feature-style' # 2. Create a CSS file on this branch $ echo "body { font-family: sans-serif; }" > style.css # 3. Stage and commit $ git add style.css && git commit -m "Add basic stylesheet" [feature-style d4e5f6] Add basic stylesheet # 4. Switch back to main — style.css disappears! $ git checkout main $ ls index.html # 5. Merge the feature branch into main $ git merge feature-style Updating abc1234..d4e5f6 style.css | 1 + # 6. Now style.css is here on main too! $ ls index.html style.css
E3

Push Your Repo to GitHub

Before starting: Go to github.com → click "New repository" → name it git-exercise → do NOT initialize with README (keep it empty) → Create repository.

Branch 'main' set up to track remote branch 'main' from 'origin'. # Visit: https://github.com/YOUR-USERNAME/git-exercise # You should see your files in the browser!
