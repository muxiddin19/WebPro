GitHub Pages & Deployment

8 topics · 3 exercises · take your site from local file to live URL

💡
Prerequisites: You have completed the Monday Git guide and pushed a repo to GitHub. Today we make that repo live on the internet using GitHub Pages — for free, in under 5 minutes.
01

What is Deployment?

Deployment means making your website accessible to the public internet. Right now your site only lives on your computer — only you can see it. Deployment puts it on a server so anyone with the URL can visit it.

There are many hosting options, each with different trade-offs. As a beginner building static HTML/CSS/JS sites, GitHub Pages is the easiest and most powerful free option.

🆓
GitHub Pages
Free, static sites. No server needed. You already know how to use it (it's just Git).
⚡
Netlify / Vercel
Free tier, very fast, auto-deploys on push. Supports more advanced builds.
🖥️
VPS / Cloud
AWS, GCP, Azure — full control but you manage the server. Costs money.
🐳
Docker / Containers
Package your app and run it anywhere. Industry standard. (We'll learn later.)

Key Points

  • Deployment = putting your site on a server so anyone can access it via URL.
  • A "static" site = only HTML, CSS, JavaScript — no server-side processing needed.
  • GitHub Pages is free, instant, and requires only git knowledge you already have.
  • For larger apps (Node.js, PHP, databases) you'll need Netlify, Vercel, or a VPS.
02

GitHub Pages Overview

GitHub Pages is a free hosting service built directly into GitHub. Every GitHub user gets one personal site (username.github.io) and unlimited project sites (username.github.io/repo-name).

There is no separate server to configure, no FTP upload, no cost. You push code with git push, and GitHub automatically deploys it within about 30–60 seconds.

🆓
Free
No cost for public repos. No credit card.
🚫
Static Only
HTML, CSS, JS only. No PHP, Node.js, or databases.
⚡
Auto-Deploy
Push → GitHub deploys automatically in ~60 seconds.
🌐
CDN-backed: GitHub Pages serves files from GitHub's global Content Delivery Network (CDN). Your site loads fast from anywhere in the world — Seoul, New York, Lagos — without any configuration.

Key Points

  • GitHub Pages = free static website hosting, built into every GitHub repo.
  • Works for HTML, CSS, JavaScript — exactly what you've been building this semester.
  • Each user gets: one personal site + unlimited project sites.
  • No server configuration, no FTP, no cost — just git push.
  • Limitation: no server-side code (PHP, Python, Node.js) or databases.
03

Step-by-Step: Enable GitHub Pages

Enabling GitHub Pages takes about 2 minutes and only needs to be done once per repository. Here is the exact walkthrough.

1
Go to your repository on GitHub

Open your browser and navigate to github.com/YOUR-USERNAME/YOUR-REPO

2
Click the "Settings" tab

It's in the top navigation bar of your repository, to the right of Insights.

3
Scroll down the left sidebar to "Pages"

Under the "Code and automation" section. Click "Pages".

Settings → Pages
4
Under "Build and deployment" → set Source to "Deploy from a branch"

This is the simplest method — GitHub reads your files directly from a branch.

5
Set the branch to "main" and folder to "/ (root)"

This tells GitHub Pages to serve your site from the root of your main branch.

Branch: main  |  Folder: / (root)
6
Click "Save"

GitHub starts building your site. Wait about 30–60 seconds.

7
Refresh the Settings → Pages page

When ready, you'll see a green banner: "Your site is live at https://YOUR-USERNAME.github.io/YOUR-REPO/" — click it!

⚠️
The repo must be Public. Private repos require GitHub Pro to use Pages. If you don't see the Pages option, check that your repo is set to Public in Settings → General.

Key Points

  • Path: Settings → Pages → Deploy from a branch → main → /(root) → Save.
  • First deployment takes 30–120 seconds. Subsequent deploys (after git push) take 30–60 seconds.
  • The repo must be Public for free Pages hosting.
  • Every git push to main automatically re-deploys your site — no extra steps needed.
04

The URL Structure

GitHub Pages gives every repository a predictable URL. Understanding the pattern lets you fix broken links, share your site, and set up custom domains.

URL Anatomy

https://jdoe.github.io/webpro-w9/about.html
jdoe
Your GitHub username
webpro-w9
Repository name
/about.html
File path in the repo

Two types of Pages sites

Personal / Organization site
https://USERNAME.github.io/
Repo must be named exactly USERNAME.github.io. Served at the root URL.
Project site (most common for students)
https://USERNAME.github.io/REPO-NAME/
Any other repo. Note the trailing slash — always include it when sharing the URL.
🌐
Custom domains: You can use your own domain (e.g., johndoe.com) by adding a CNAME file to the repo and configuring your domain's DNS settings. GitHub Pages supports this for free. We won't cover it in class, but the GitHub Docs guide is excellent.

Key Points

  • Project site URL: https://USERNAME.github.io/REPO-NAME/
  • Personal site URL: https://USERNAME.github.io/ (repo must be named USERNAME.github.io)
  • File paths in the repo map directly to URL paths. /about.html → /about.html in the URL.
  • Custom domains are supported and free — just requires DNS configuration.
05

What Works & What Doesn't

GitHub Pages serves static files only. When someone visits your URL, GitHub's server reads the file from your repo and sends it directly. There is no PHP interpreter, no Python runtime, no database — just files.

Compatibility Table

TechnologyWorks on Pages?Why / Why not
HTML✓ YesStatic file — GitHub serves it directly.
CSS✓ YesStatic file — just downloaded by the browser.
JavaScript (client-side)✓ YesRuns in the visitor's browser — no server needed.
fetch() / Axios (external APIs)✓ YesThe browser calls the external API — nothing server-side.
Images, fonts, PDFs✓ YesStatic files — just stored in the repo.
PHP✗ NoRequires a PHP interpreter running on the server.
Node.js / Express✗ NoRequires a Node.js runtime — use Render, Railway, or Heroku.
Python / Django / Flask✗ NoRequires a Python runtime. Not available on Pages.
MySQL / MongoDB✗ NoDatabases need a running server process — not possible.
Server-side sessions / auth✗ NoRequires server-side processing. Use Firebase or Auth0 instead.
🎯
Rule of thumb: If it runs in the browser → it works. If it needs a server process → it doesn't. Your Book Search App from Week 6–7 uses fetch() to call an external API — that all runs in the browser, so it works perfectly on Pages!

Key Points

  • HTML, CSS, client-side JS → all work on GitHub Pages.
  • PHP, Node.js, Python, databases → do NOT work. They require a server process.
  • fetch() to external APIs works because it runs in the visitor's browser.
  • If you need server-side logic, use Netlify Functions, Vercel Serverless, or a separate backend.
06

index.html is Everything

When someone visits your GitHub Pages URL without specifying a file (https://you.github.io/webpro-w9/), the server automatically looks for index.html and serves it. This is the entry point of your site. Without it, visitors get a 404 error.

Good project structure for GitHub Pages

webpro-w9/ ← your repo root ├── index.html ← REQUIRED: the homepage ├── about.html ← extra pages ├── css/ │ └── style.css ├── js/ │ └── app.js ├── images/ │ └── banner.jpg └── 404.html ← optional: custom "not found" page

URL to file mapping

/webpro-w9/→ serves index.html
/webpro-w9/about.html→ serves about.html
/webpro-w9/images/banner.jpg→ serves the image
/webpro-w9/nonexistent.html→ serves 404.html (if it exists)
⚠️
Use relative paths, not absolute paths. Instead of href="/css/style.css", use href="css/style.css" or href="./css/style.css". Absolute paths starting with / will break on project sites because the root is /webpro-w9/, not /.

Key Points

  • index.html in the repo root is required — it's the homepage.
  • File paths in the repo map directly to URL paths.
  • Use relative paths (./style.css, not /style.css) to avoid breakage.
  • Create a custom 404.html for a friendly "page not found" experience.
07

GitHub Actions Introduction

GitHub Actions is GitHub's built-in automation system. It runs tasks automatically when events happen in your repo (like pushing code). The automation is described in YAML files called workflows.

For now, GitHub Pages handles deployment automatically — but understanding Actions helps you see how modern CI/CD (Continuous Integration / Continuous Deployment) works.

Example: Simple GitHub Actions Workflow

# File: .github/workflows/deploy.yml # This runs every time you push to main name: Deploy to Pages on: push: branches: [ main ] jobs: deploy: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Deploy uses: peaceiris/actions-gh-pages@v3 with: github_token: ${{ secrets.GITHUB_TOKEN }} publish_dir: ./
CI — Continuous Integration
Automatically test your code every time you push. Catch bugs before they reach users.
CD — Continuous Deployment
Automatically deploy to production every time tests pass. Ship faster, more reliably.
💡
Good news: When you use the built-in GitHub Pages "Deploy from branch" method, GitHub Actions is already running behind the scenes — you just don't have to configure it. You'll configure it manually when you need build steps (like compiling React or Vue).

Key Points

  • GitHub Actions = automation triggered by repo events (push, pull request, schedule, etc.).
  • Workflows are defined in YAML files inside .github/workflows/.
  • CI = run tests automatically. CD = deploy automatically when tests pass.
  • For simple static sites, GitHub's built-in Pages handles deployment — no workflow file needed.
08

Practical Deployment Checklist

Before you push to GitHub and share your live URL, run through this checklist. These are the most common reasons a site looks different in production than on your local machine.

  • 🔗
    Check all file paths are relative

    Replace href="/css/style.css" with href="css/style.css". Absolute paths break on project sites because the root is /REPO-NAME/.

  • 🖼️
    Check image paths and filenames

    GitHub's servers are case-sensitive. Images/Banner.jpg and images/banner.jpg are different files. Lowercase everything.

  • 🧹
    Remove console.log() calls

    Not required, but professional practice. console.log() is for debugging — leave it in code you ship only if it serves a purpose.

  • 🔑
    Never commit API keys or secrets

    Everything in a public GitHub repo is visible to the world. Never put API keys, passwords, or tokens in your committed files — use environment variables or a backend proxy.

  • ✅
    Test locally before pushing

    Use VS Code's Live Server extension or open index.html directly in your browser. Fix errors locally before deploying.

  • 🌐
    Verify the live URL works

    Open your https://USERNAME.github.io/REPO-NAME/ URL in a private browser tab (to avoid cache). Test on mobile too.

  • 📁
    Confirm index.html is in the root

    Not inside a subfolder. GitHub Pages serves the root of the selected branch. The homepage must be at index.html, not src/index.html.

Key Points

  • Relative paths (./style.css) not absolute (/style.css) — the most common deployment bug.
  • Filenames are case-sensitive on GitHub's servers — use consistent casing.
  • Never commit secrets; always check your repo is working locally before pushing.
  • Test the live URL in an incognito/private window to avoid browser cache issues.
